# FUSE judging narration

## A · One wallet approval for a complete route

A Bitcoin Cash wallet can pay someone in one transaction. A trade that needs a loan, two liquidity pools and a repayment is harder. Every contract has to accept the same set of inputs and outputs. FUSE builds that transaction and lets the wallet holder inspect the cost before approving it. We can trace one recorded execution all the way to a confirmed block.

## B · Borrowing from a FlashVault

The vault is an unspent BCH output carrying an identity NFT. Spending it makes its principal available within that transaction. The covenant checks that the same script and NFT return at the same index, with the required fee and the updated counter. In the recorded negative test, a repayment one satoshi short failed in the local Bitcoin Cash virtual machine.

## B · One purchase, one sale, one repayment

Follow the two-pool transaction in block nine hundred seventy-eight thousand two hundred fourteen. The first pool received five thousand three hundred six satoshis for one unit of Paryon USD. The second returned five thousand two hundred seventy-three. The trade lost thirty-three satoshis. Including the vault fee and miner fee, the wallet spent one thousand nine hundred ninety-one satoshis. The receipt lets a judge check both pool continuations and the repayment.

## C · Two signed quotes at the same cost

In a separate mainnet run, two solver processes answered a signed request for a quote. Both belonged to the operator. FUSE verified the signatures and recomputed both routes. Both cost the user one thousand nine hundred ninety-one satoshis. The quote hash broke the tie. The winning quote, the authorization, and the settlement are linked in the evidence index.

## D · Cashonize pairs over WizardConnect

Here is the real pairing prompt from Cashonize. The wallet asks permission to share its address information with the application. The captured session used the first receive address. The server handles a public signing package, and the wallet keeps the spending key.

## D · The wallet approves an exact transaction

This is the captured signing prompt. Cashonize version zero point sixteen approved the wallet input of a mainnet flash transaction. It preserved the covenant unlock and used signatures committing to all outputs and source outputs. The resulting transaction is confirmed in block nine hundred seventy-eight thousand two hundred forty-six. This establishes one wallet and one action.

## E · Checking a receipt

A certificate can carry several kinds of evidence. Inclusion links transaction bytes to a block. Structure compares the inputs and outputs. Outcome verification recomputes repayment, fees and pool rules. Intent binding compares the chain transaction with the signed authorization. Here the sandbox verifier accepts its original receipt.

## E · The altered receipt fails

After changing the receipt, verification fails. This screen is a sandbox demonstration. For mainnet, the submission includes the raw transactions, parent outputs and Merkle branches. Those records exposed incorrect block heights in the original certificates. The corrected receipts preserve the same transaction IDs.

## F · Guardian and Parallel Worlds

Guardian reads Paryon loan state and reports its coverage. Parallel Worlds uses simulated funds to compare what happens when a vault is paused. Developers can run the SDK quickstart locally and verify a sandbox certificate. Paryon loan management and automated mainnet trading are outside this release.

## G · Where a protocol can start

Wallet developers can start with the signing request. Protocol teams can inspect the transaction composer, and solver operators can examine the quote transcript. Liquidity providers can inspect exactly what the owner-controlled vault receives. Open the evidence index or the public verifier to check the claims using the same transaction IDs.
